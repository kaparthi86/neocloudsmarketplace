1. Goals and non-goals

Goals

GoalDesign implication
Unused → onlineProviders list idle accelerators; live nodes require agent presence
Low / transparent costListed $/hr in catalog; payments disabled in early access
OpenOpen APIs, open catalog axes, open-source control plane
Trust asymmetry reducedChallenge attest (identity) ≠ heartbeat (liveness)
Builder-friendlyREST + OpenAI-compatible inference surface

Non-goals (current generation)

  • Automatic SSH user / container provisioning on provider hosts
  • Payments, escrow, or payouts
  • Cross-cloud job scheduler (Sky-style planner is a future consumer)
  • Confidential computing / TEE-backed isolation
  • Guaranteed SLA fleets at hyperscaler scale

2. Design principles

  1. Separate catalog truth from demo UX. Seeded inventory may be simulated; live nodes are explicit and gated by attest + heartbeat.
  2. Thin provider integration. Host-side neo-agent is enough to go live.
  3. Availability is derived. Computed from attestation, heartbeat TTL, and reservation conflicts.
  4. Workload-aware discovery. Hardware × workload tags × price.
  5. Honest early access. UI/API advertise simulated vs live; no payment collection.

6. Live hardware connect (agent protocol)

Aligned with the research paper: attestation ≠ liveness. Attest proves identity; heartbeat proves the node is online now.
sequenceDiagram
  participant P as Provider console
  participant API as Control plane
  participant A as neo-agent
  participant C as Customer
  P->>API: POST /v1/nodes live true
  API-->>P: node_id
  A->>API: attest challenge
  API-->>A: nonce
  A->>API: attest verify
  API-->>A: attested
  loop every 30s
    A->>API: heartbeat
    API-->>A: online + pending
  end
  P->>API: create listing
  C->>API: reserve
  API-->>C: pending_provision
  A->>API: pending + ack
  API-->>C: active + connection_info

Availability predicate (live)

  1. Node exists and attestation_status === attested
  2. Fresh heartbeat within TTL (default 90s)
  3. No conflicting active / pending_provision reservation
MethodPathPurpose
POST/v1/agent/heartbeatMark online
POST/v1/nodes/:id/attest/challengeIssue nonce
POST/v1/agent/attest/verifyBind fingerprint proof
GET/v1/agent/nodes/:id/pendingList pending jobs
POST/v1/agent/reservations/:id/ackSSH / connection details

Host binary: scripts/neo-agent.mjs.

13. Key sequences

Seller (live)

  1. Provider key → /console.html
  2. Register live node
  3. Run neo-agent
  4. Publish listing
  5. Ack customer reservations

Buyer

  1. Browse /marketplace
  2. Get customer API key
  3. Reserve hours
  4. LIVE → wait for active + connection_info
  5. SIMULATED → demo reservation only

14. Summary

Neo Clouds is a marketplace control plane: auth, node identity, listing discovery, reservation lifecycle, and an agent protocol that binds live supply to attested, heartbeating hosts. It ships an open unused-accelerator exchange first, then grows toward matching, secure multi-tenancy, and measured utilization.
